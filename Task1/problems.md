## 1. Перегруженность DWH (вся бизнес логика)

* Весь SQL Server DWH содержит не только данные, но и значительную часть бизнес-логики.
* DWH используется как центр интеграции между доменами (медицинским, финтехом, ИИ).

| Бизнес-сценарий                         | Проблема                                                        |
|-----------------------------------------|-----------------------------------------------------------------|
| Быстрое принятие управленческих решений | Сложные SQL-процедуры работают часами, отчёты долго формируются |
| Быстрое развитие новых направлений      | Добавление новой логики ломает существующие процессы и отчёты   |
| Независимость доменов                   | Любое изменение в медицине или финтехе требует правок в DWH     |

## 2. Немасшатибруемость SQL Server

* Сервер не масштабируется горизонтально.
* Вычисления идут на одном хосте.
* Невозможно эффективно хранить/обрабатывать большие объемы данных.

| Сценарий                      | Потери                                                                   |
|-------------------------------|--------------------------------------------------------------------------|
| Быстрая подготовка отчётности | Большие объёмы пораждают долгие запросы, нагрузка растёт экспоненциально |
| Масштабирование бизнесов      | Новые домены добавляют ещё больше нагрузки                               |

## 3. Неоднородность данных в одном монолитном DWH

* Медицинские данные (медкарты) + финансовые данные + HR + инвентарь в одной базе.
* Связность таблиц.
* Невозможно выделить отдельные домены без глубокого рефакторинга.

| Сценарий                     | Потери                                           |
|------------------------------|--------------------------------------------------|
| Независимое развитие доменов | Невозможно развивать финтех отдельно от медицины |
| Подключение новых бизнесов   | Новому направлению придется жить в DWH           |

## 4. Существующая интеграция через старую шину (Camel)

* Шина выполняет точечные синхронные интеграции.
* Не держит высокую нагрузку.
* Нет событийной модели.

| Сценарий                           | Потери                                                |
|------------------------------------|-------------------------------------------------------|
| Масштабирование для новых бизнесов | Каждый новый партнёр → новый набор сложных интеграций |
| Быстрое развитие ИИ                | Обмен медданными медленный, нерегламентированный      |
| Повышение отказоустойчивости       | При падении шины ломаются все интеграции              |

## 5. BI-система зависит напрямую от DWH

* Power BI делает прямые запросы в DWH.
* При обновлении данных могут тормозить и DWH, и BI.
* Активное использование кастомных вычислений (DAX), перетягивающих нагрузку на BI.

| Сценарий                   | Потери                                            |
|----------------------------|---------------------------------------------------|
| Быстрая подготовка отчётов | BI ждёт DWH, DWH ждёт BI                          |
| Снижение time-to-market    | Любой новый отчёт требует подготовки данных в DWH |

## 6. Медицинские данные используются для аналитики напрямую

* Медкарты, исследования и сырые диагностические данные поступают в DWH.
* Это нарушает принципы безопасности и требования регуляторов.

| Сценарий                                | Потери                                                               |
|-----------------------------------------|----------------------------------------------------------------------|
| Соответствие регуляторам (медицина/PII) | Риски штрафов, аудит, невозможность открыть новые бизнес-направления |
| Развитие аналитики                      | Нельзя гибко работать с такими чувствительными данными               |

## 7. ИИ-сервисы интегрируются напрямую с DWH/шиной

* ИИ получает медицинские данные в режиме «point-to-point».
* Нет выделенного API для моделей.
* Нет стандартизированного потока событий.

| Сценарий               | Потери                                                |
|------------------------|-------------------------------------------------------|
| Развитие ИИ            | Модели сложно обновлять, трудно получать поток данных |
| Масштабирование        | Нельзя обучать новые модели параллельно               |
| Безопасность медданных | Доступ ИИ к полным данным повышает риски              |

## 8. Слабая отказоустойчивость

* Нет геораспределённого деплоя.
* DWH — single point of failure.

| Сценарий                  | Потери                                         |
|---------------------------|------------------------------------------------|
| Операционная стабильность | Падение SQL Server → клиники не работают       |
| Финтех-операции           | Невозможность проводить транзакции             |
| BI-отчётность             | Любой простой блокирует управленческие решения |

## 9. Отсутствие единого каталога данных и ролевой модели

* Нет Data Catalog.
* Нет централизованных политик доступа.
* Нет истории изменении данных.

| Сценарий                | Потери                                                      |
|-------------------------|-------------------------------------------------------------|
| Поддержка безопасности  | Трудно контролировать доступ к мед/фин данным               |
| Точная отчётность       | Частые ошибки из-за неизвестного источника данных           |
| Масштабирование доменов | Нельзя централизованно управлять доступами для новых команд |

## 10. Медленное создание новых отчётов и изменений

* Каждый новый отчёт требует ресурсов команды разработки.
* BI-прослойки очень кастомные.

| Сценарий           | Потери                                              |
|--------------------|-----------------------------------------------------|
| Time-to-market     | Бизнес ждёт недели/месяцы                           |
| Финтех-риск-оценка | Отчёты могут устаревать быстрее, чем готовятся      |
| Вывод новых услуг  | Аналитика для бизнес-кейсов готовится слишком долго |
